# POSMAN — Bootstrap Gate 02/03

## Shared Tauri + React desktop shell before parallel execution

This is a short integration gate between accepted PHASE 01 and the parallel
execution of PHASE 02 and PHASE 03.

It is not a new product phase. Its only purpose is to create one accepted,
shared desktop-project structure so the runtime and UI executors do not create
conflicting manifests, Tauri configuration, or source roots.

## 5. Frontend bootstrap boundary

The frontend must be intentionally minimal.

Create:

- A valid React root.
- A single `AppRoot` bootstrap component.
- A minimal semantic `<main>` landmark.
- A small local CSS reset sufficient to verify rendering.
- Arabic document defaults:

```html

```

- A visible bootstrap message identifying the shell as POSMAN and explicitly
  indicating that the design system is pending PHASE 03.

Do not create:

- A dashboard.
- Sidebar navigation.
- Cards, charts, tables, forms, dialogs, notifications, or business screens.
- Final branding or a final logo.
- Generic admin-template styling.
- Glassmorphism, gradients, bento layouts, decorative animation, or placeholder
  marketing content.

The bootstrap UI exists only to prove that React renders inside the Tauri
window. PHASE 03 owns the real design.

Use logical CSS properties where direction is relevant. Do not introduce
left/right assumptions that would obstruct Arabic RTL or French LTR later.

## 7. Rust bootstrap boundary

Keep Rust deliberately small:

- Standard Tauri builder/bootstrap.
- `lib.rs` contains the application setup used by both desktop entry and tests.
- `main.rs` delegates to the library entry point according to current Tauri
  project conventions.
- No database connection.
- No migration runner.
- No `rusqlite`.
- No commands for products, users, stock, sales, accounting, files, backups, or
  printing.
- No network client.
- No hidden sidecar or local server.
- No unsafe Rust unless the platform template strictly requires it and the
  reason is documented.

A trivial deterministic shell-health command is not required. If the current
official template creates a greeting command, remove it rather than keeping
demo functionality that is not part of POSMAN.

The native project must compile without warnings under the configured checks.
