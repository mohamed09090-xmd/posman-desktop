## 2. رؤية المنتج

POSMAN برنامج إدارة تجارية محلي يساعد التاجر الجزائري على إدارة المواد، العملاء،
الموردين، المخزون، المبيعات، المشتريات، المستندات والقيود المحاسبية من واجهة واحدة
واضحة.

يجب أن يستطيع مستخدم جديد:

1. تثبيت البرنامج من ملف واحد.
2. إدخال معلومات شركته.
3. إضافة مادة ومستودع وعميل.
4. إدخال مخزون افتتاحي.
5. تنفيذ عملية بيع وطباعة فاتورة.

وذلك دون تثبيت PostgreSQL أو Node.js أو Docker أو أي مكوّن تطوير.

### وعد المنتج

> من أول تثبيت إلى أول فاتورة، بخطوات مفهومة ومن دون تعقيد برامج ERP التقليدية.

## 4. مبادئ تجربة المستخدم

### 4.1 الوضوح قبل الكثافة

- تُعرض المعلومات اللازمة لاتخاذ القرار فقط.
- الحقول المتقدمة تكون داخل قسم «خيارات إضافية».
- لا تُعرض أعمدة غير مهمة افتراضيًا.
- يمكن لكل مستخدم حفظ ترتيب الأعمدة المناسب له.

### 4.2 لغة بشرية

أمثلة:

- «الكمية المتاحة 8 فقط» بدل `INSUFFICIENT_STOCK`.
- «لا يمكن تعديل الفاتورة بعد ترحيلها» بدل خطأ قاعدة بيانات.
- «أنشئ مستودعًا أولًا لإدخال المخزون» بدل صفحة فارغة.

### 4.3 نفس النمط في جميع المستندات

كل مستند تجاري يتكون من:

1. رأس المستند.
2. جدول المواد.
3. الخصومات والضرائب.
4. المجاميع.
5. شريط الإجراءات.
6. سجل التحويلات والتغييرات.

### 4.4 الإفصاح التدريجي

- المستخدم المبتدئ يرى المسار الأساسي.
- المستخدم المحترف يصل إلى الاختصارات والخيارات المتقدمة.
- لا يُطلب من المستخدم اتخاذ قرارات تقنية.

### 4.5 الأداء

- لا مؤثرات ثقيلة.
- لا صور زخرفية أو فيديوهات.
- لا تحميل بيانات ضخمة دفعة واحدة.
- الجداول الطويلة تستخدم virtualization.
- البحث والتصفية يجب أن يبقيا سريعين على جهاز بذاكرة 4GB.

## 5. اتجاه التصميم: دفتر العمليات المعاصر

### 5.1 الشخصية البصرية

- دقيقة وواثقة وهادئة.
- تجارية وليست مصرفية جامدة.
- حديثة دون تقليد قوالب SaaS.
- عملية أكثر من كونها استعراضية.

### 5.2 ما لن نستخدمه

- Glassmorphism.
- تدرجات زرقاء أو بنفسجية عامة.
- Bento Grid.
- شبكة بطاقات KPI متكررة.
- حواف مستديرة كبيرة.
- Sidebar مأخوذ من قالب Admin.
- زخارف 3D أو صور مخزنة.
- حركة لا تشرح تغييرًا فعليًا.

### 5.3 النظام البصري المبدئي

| Token | القيمة |
|---|---|
| الخلفية الرئيسية | `#F4F0E7` |
| سطح المستند | `#FFFCF6` |
| النص الأساسي | `#1E2523` |
| النص الثانوي | `#66706C` |
| الحدود | `#D8D0C2` |
| الحالة المؤكدة | `#1F5A45` |
| الانتظار | `#B7791F` |
| الخطأ أو النقص | `#B74A3C` |
| نصف القطر | 4px إلى 6px |
| المسافات | 4 / 8 / 12 / 16 / 24 / 32 |
| الخط المقترح | IBM Plex Sans Arabic / IBM Plex Sans |

### 5.4 مكونات الهوية

- `Command Bar`: شريط الأوامر العام.
- `Workspace Rail`: التنقل بين مساحات العمل.
- `Document Canvas`: مساحة تحرير المستند.
- `Process Strip`: طلب ← تسليم ← فاتورة ← محاسبة.
- `Status Stamp`: حالة المستند بشكل يشبه ختمًا تشغيليًا.
- `Data Grid`: جدول عملي قابل للتخصيص.
- `Detail Drawer`: تفاصيل جانبية دون فقدان موضع المستخدم.
- `Action Dock`: إجراءات الحفظ والتأكيد والطباعة.

### 5.5 الحركة

- 120ms إلى 180ms للتغذية الراجعة البسيطة.
- الحركة تشرح فتح لوحة، نجاح الحفظ أو انتقال الحالة.
- دعم `prefers-reduced-motion`.
- لا انتقالات تؤخر البيع أو إدخال الكميات.

## 9. دورات العمل الأساسية

### 9.1 المخزون الافتتاحي

```text
إنشاء جلسة مخزون افتتاحي
→ اختيار المستودع والتاريخ
→ إدخال المادة والكمية والتكلفة
→ مراجعة المجاميع
→ ترحيل
→ إنشاء حركات OPENING
→ تحديث رصيد المخزون
```

لا يُعدّل الرصيد مباشرة.

### 9.2 الشراء

```text
طلب/أمر شراء
→ استلام جزئي أو كامل
→ حركة دخول للمخزون
→ فاتورة مورد
→ مطابقة الكميات والأسعار
→ قيد محاسبي
→ دفع جزئي أو كامل
```

### 9.3 البيع الآجل

```text
طلب عميل
→ تأكيد
→ حجز كلي أو جزئي
→ سند تسليم للكميات المتاحة
→ ترحيل خروج المخزون
→ فاتورة للكميات المسلّمة فقط
→ قيد محاسبي
→ تحصيل جزئي أو كامل
```

### 9.4 البيع المباشر

```text
فاتورة بيع مباشرة
→ التحقق من المخزون
→ إنشاء حركة تسليم داخلية
→ ترحيل المخزون والفاتورة معًا
→ إنشاء القيد
→ طباعة أو تصدير PDF
```

### 9.5 المرتجع

```text
اختيار المستند الأصلي
→ تحديد الأسطر والكميات
→ إنشاء مستند مرتجع
→ حركة مخزون عكسية
→ إشعار دائن أو قيد عكسي
```

لا يُعدّل المستند الأصلي.

## 10. حالات المستندات

### طلب العميل

`DRAFT → CONFIRMED → PARTIALLY_DELIVERED → DELIVERED → CLOSED`

مع حالات استثنائية:

`CANCELLED`, `ON_HOLD`

### سند التسليم

`DRAFT → RESERVED → POSTED → PARTIALLY_INVOICED → INVOICED`

### فاتورة البيع

`DRAFT → VALIDATED → POSTED → PARTIALLY_PAID → PAID`

مع:

`CREDITED`, `REVERSED`

### استلام الشراء

`DRAFT → POSTED → PARTIALLY_INVOICED → INVOICED`

## 11. قواعد المستندات والتحويل

- التحويل يكون على مستوى السطر والكمية.
- يمكن تحويل مستند واحد إلى عدة مستندات.
- يمكن تجميع مستندات متوافقة في فاتورة واحدة وفق قواعد واضحة.
- الكمية المحولة لا تتجاوز الكمية المتبقية.
- كل تحويل يحفظ رابط المصدر والهدف والمستخدم والتاريخ.
- المستند المرحّل غير قابل للحذف.
- التصحيح يكون بعكس أو مرتجع.
- أرقام المستندات منفصلة عن المعرفات الداخلية.
- الضغط المكرر على زر الترحيل لا يكرر الحركة.

## 12. قواعد المخزون

### الكميات

```text
On Hand - Reserved = Available
```

### مصدر الحقيقة

`stock_movements` هو السجل المرجعي.  
`stock_balances` ملخص سريع يعاد بناؤه من الحركات عند الحاجة.

### أنواع الحركات

- `OPENING`
- `PURCHASE_RECEIPT`
- `SALES_DELIVERY`
- `SALES_RETURN`
- `PURCHASE_RETURN`
- `TRANSFER_OUT`
- `TRANSFER_IN`
- `ADJUSTMENT_IN`
- `ADJUSTMENT_OUT`
- `COUNT_VARIANCE`

### تكلفة المتوسط المتحرك

عند الاستلام:

```text
New Average Cost =
((Old Quantity × Old Average Cost) + (Received Quantity × Receipt Cost))
÷ (Old Quantity + Received Quantity)
```

لا يُعاد حساب تكلفة عمليات خرج قديمة عند تغيير التكلفة مستقبلًا.

## 13. قواعد الأسعار والضرائب

### طريقة هامش التكلفة

```text
Sale Price HT = Cost Price HT × (1 + Margin Rate)
```

### طريقة الهامش من سعر البيع

```text
Sale Price HT = Cost Price HT ÷ (1 - Mark Rate)
```

تُحفظ الطريقة المستخدمة في إعدادات المؤسسة.

### ترتيب الحساب

1. الكمية × سعر الوحدة.
2. خصم السطر.
3. توزيع الخصم العام.
4. تحديد الوعاء الضريبي.
5. حساب الضريبة.
6. التقريب.
7. حساب HT وTax وTTC.

### الضرائب

- النسب قابلة للتعديل ولا تُكتب داخل الكود.
- لكل نسبة تاريخ بداية ونهاية صلاحية.
- تحفظ الفاتورة نسخة من النسبة والاسم وقت الإصدار.
- يدعم السعر HT أو TTC حسب إعداد المؤسسة.

## 14. الترحيل المحاسبي

### المبدأ

قواعد الترحيل قابلة للتهيئة حسب مخطط حسابات المؤسسة. لا تُكتب أرقام الحسابات
داخل منطق البرنامج.

### أمثلة منطقية

| الحدث | المدين | الدائن |
|---|---|---|
| فاتورة بيع | حساب العميل | المبيعات + الضريبة المحصلة |
| فاتورة شراء | المخزون/المشتريات + الضريبة القابلة للاسترجاع | حساب المورد |
| تسليم بضاعة | تكلفة المبيعات | المخزون |
| مردود | حسابات عكسية حسب المستند |

### ضوابط

- مجموع المدين يساوي مجموع الدائن.
- قيد واحد فقط لكل حدث.
- القيد المرحّل غير قابل للتعديل.
- التصحيح بقيد عكسي.
- لا ترحيل داخل فترة مغلقة.
- حالات فشل الترحيل تظهر بلغة واضحة ويمكن إعادة المحاولة.

### الحدود

- الواجهة لا تنفذ SQL مباشرة.
- الواجهة لا تحدد صحة الترحيل.
- Rust يعيد حساب الأسعار والمجاميع.
- كل عملية حساسة تعمل داخل transaction.
- واجهة Tauri Commands هي العقد المحلي بين UI والمنطق.

## 16. استراتيجية SQLite

### إعدادات

- تفعيل `PRAGMA foreign_keys = ON`.
- استخدام WAL عند ملاءمته.
- migrations مرقمة وتُطبق تلقائيًا.
- فحص سلامة عند الاستعادة.
- لا تخزين أموال باستخدام `REAL`.

### أنواع البيانات المالية

لتجنب أخطاء الفاصلة العائمة:

- المبالغ النهائية: عدد صحيح بوحدة السنتيم، Scale 2.
- سعر الوحدة والتكلفة: Fixed-point، Scale 4.
- الكميات: Fixed-point، Scale 6.
- التحويل والحساب يتمان بواسطة Decimal في Rust.

### المعرفات والتواريخ

- UUID كنص للمعرف الداخلي.
- أرقام المستندات كسلاسل منفصلة.
- التوقيت محفوظ بصيغة ISO 8601.
- التاريخ التجاري محفوظ مستقلًا عن وقت إنشاء السجل.

## 23. معايير قبول النسخة الأولى

### التثبيت

- يعمل Setup على Windows نظيف دون تنزيل خارجي.
- لا يحتاج المستخدم إلى قاعدة بيانات منفصلة.
- تُنشأ قاعدة البيانات تلقائيًا.

### الإعداد

- يستطيع المستخدم إنهاء معالج الإعداد.
- يستطيع إنشاء مستودع ومستخدم وإعداد الضرائب.

### المخزون

- المخزون الافتتاحي ينشئ حركات صحيحة.
- استلام شراء يرفع الكمية ويحدث CUMP.
- التسليم يخفض المخزون مرة واحدة.
- لا يمكن بيع كمية غير متاحة دون صلاحية.

### دورة البيع

- طلب 20 وحدة يمكن تسليم 8 ثم 12.
- لا تتكرر الكميات المحولة.
- الفاتورة تنشأ من الكمية المسلّمة فقط.
- البيع المباشر ينشئ حركة مخزون وقيدًا واحدًا.

### المحاسبة

- كل قيد متوازن.
- لا يتكرر القيد عند الضغط مرتين.
- لا تعدل القيود المرحلة.
- الفترة المغلقة تمنع الترحيل.

### المستندات

- يمكن طباعة وحفظ فاتورة PDF.
- تحمل الفاتورة هوية المؤسسة.
- إعادة الطباعة تستعمل النسخة التاريخية الصحيحة.

### النسخ الاحتياطي

- تنجح نسخة احتياطية أثناء وجود البيانات.
- تُرفض النسخة التالفة.
- تُستعاد نسخة سليمة دون فقدان غير مقصود.

### سهولة الاستخدام

- مستخدم جديد يستطيع إضافة مادة وتنفيذ بيع دون شرح تقني.
- كل خطأ يشرح السبب والخطوة التالية.
- كل إجراء خطير يعرض أثره قبل التنفيذ.
